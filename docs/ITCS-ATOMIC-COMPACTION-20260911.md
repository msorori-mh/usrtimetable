# المرحلة الثانية: حفظ خطة التحسين كاملة

الهدف: إغلاق احتمال بقاء نقل تمهيدي محفوظًا وحده عند فشل خطوة لاحقة. النطاق هو الحفظ الذري، حماية المعاينة من تغير المدخلات، واستعادة معرفة النتيجة بعد انقطاع الاتصال. تبقى خوارزمية البحث ذات النقل المباشر والنقل المترابط من خطوتين كما هي.

## خط الأساس والنطاق

- المستودع: `msorori-mh/usrtimetable`؛ امتداد لطلب المراجعة 148 بعد `1ece8f14a933eabe805e09f3d2d9c3c215d043bd`.
- المشروع المستهدف هو timetable، ومعرّف Lovable هو `c14ffafc-2bc4-44f0-aef6-c8785e7ca67b`. لا تستخدم اتصال قاعدة بيانات مشروع آخر.
- بيانات الإدخال الأخيرة حُذفت في المرحلة السابقة. لا تتضمن هذه المرحلة إعادة إدخالها أو إعادة تنفيذ الحذف.
- مصدر SQL جاهز للمراجعة والاختبار في `supabase/sql/atomic_schedule_compaction.sql`. لا تعني إضافته إلى المستودع تطبيقه على الإنتاج.

## عقد الحفظ

1. يقرأ العميل مراجعة النسخة ووقت تحديثها قبل تحميل الصفحات وبعده. يرفض القراءة إذا تغير أحدهما، ثم يطابق بصمة المعاينة ويختبر صلاحية الخطة وفائدتها محليًا.
2. يرسل طلبًا واحدًا يتضمن معرّف عملية، والنسخة والكلية، ومراجعة المعاينة، والتنقلات المرتبة وطابع التحديث الأصلي لكل محاضرة. الحد 512 خطوة و1 ميغابايت من التنقلات.
3. يعيد الخادم التحقق من هوية المستخدم وإدارته للكلية، ومن كون النسخة مسودة، وانتماء الجلسات والقاعات، وأقفال الجلسات، وعدم كونها أصلًا مستبدلًا بالتقسيم، وثبات المدة.
4. يستخدم قفل دورة حياة النسخة الحالي. يحاول أقفال النسخة والجلسات والإسنادات دون انتظار عند احتمال انعكاس ترتيب الأقفال مع إجراءات التحرير الحالية؛ يعيد حالة انشغال بدل تكوين انتظار متبادل.
5. ينفذ الخطوات باستدعاء `move_or_reschedule_schedule_session` الحالي، بما فيه فحوص الإسناد وساعاته والتعارضات والتحذيرات. يضيف منع زيادة تجاوز أيام المستوى فوق خمسة، وفحص إغلاقات القاعات الأسبوعية والمحددة بتاريخ.
6. إذا رُفضت خطوة أو فشل سجل التدقيق، تتراجع كل الخطوات ومراجعات النسخة وسجلات التدقيق وإيصال العملية في المعاملة نفسها. لا توجد كتابة مباشرة بديلة من العميل إلى جدول الجلسات.
7. عند النجاح يُحفظ إيصال خاص بالعملية والمستخدم والكلية والنسخة وبصمة الطلب. إعادة الطلب نفسه تعيد النتيجة السابقة؛ استخدام معرّف العملية مع طلب مختلف يُرفض.

إيصالات النجاح في جدول جديد محمي بـRLS، دون منح وصول مباشر لـ`anon` أو `authenticated` أو `service_role`. تُقرأ فقط من الإجراء المصرح به للمستخدم نفسه. لم يُستخدم سجل التدقيق كإيصال موثوق لأن سياساته الحالية تسمح بإدخالات من العميل. لا تُعدّل هذه المرحلة تلك السياسات.

تُوسّع تغطية مراجعة النسخة لتشمل الدفعات، ومجموعات التقديم، وشرائح الطلاب وروابطها، وأنواع المدرسين، وإغلاقات القاعات، وإعدادات الجدولة، ومكونات الخطة، والاستراحات المسجلة، والفصول. تستعمل المحفزات الجديدة آلية الإبطال الحالية داخل الكلية. لا تُنشئ استراحات؛ يبقى إعداد الكلية صفرًا.

فحص إغلاقات القاعات المحددة بتاريخ يطابق يوم المحاضرة ضمن تقاطع الإغلاق والفصل الدراسي. عند نقص تاريخ بداية الفصل أو نهايته مع وجود إغلاق محدد بتاريخ، يُرفض الحفظ وتُطلب البيانات اللازمة. هذا يصحح حدًا في الإصدار السابق: إجراء النقل القديم لا يفحص `room_unavailability`.

## الاتصال والإلغاء

- الإلغاء قبل الإرسال لا يكتب شيئًا. بعد الإرسال تنتظر الواجهة نتيجة الدفعة ولا تعرض إلغاءً وهميًا لمعاملة قاعدة البيانات.
- عند فقدان الرد يُقرأ الإيصال. غيابه وحده لا يثبت الفشل، إذ قد تكون المعاملة لا تزال جارية؛ تظهر النتيجة غير مؤكدة.
- زر «تحقق واستكمل الحفظ» يعيد الطلب الأصلي نفسه وبمعرّف العملية نفسه. لا ينشئ خطة جديدة ولا يغير مراجعتها. إذا اصطدم بمحاولة أصلية ما زالت جارية، تبقى الحالة غير مؤكدة حتى التحقق.
- تُقرأ المؤشرات من الجدول الفعلي بعد النتيجة. إذا تأكد الحفظ وتعذر تحديث العرض، يبقى تأكيد الحفظ ظاهرًا ويُطلب تحديث الصفحة.
- تُحفظ بيانات الطلب المعلق في ذاكرة الواجهة فقط. إعادة تحميل الصفحة تزيلها؛ يمكن مراجعة الجدول وسجل التدقيق، ولا تُدّعى معرفة نتيجة الطلب القديم من دون إيصال.

## مكونات التغيير والتحقق

| المكوّن                                                    | التغيير                                                                                         |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `compact.ts`                                               | مراجعة النسخة ضمن لقطة المعاينة                                                                 |
| `compact-service.ts`                                       | قراءة متسقة، دفعة واحدة، إيصال، واستكمال الطلب الأصلي                                           |
| `compact-panel.tsx`                                        | حالة حفظ كاملة، إلغاء صحيح، ورسائل واستكمال بعد انقطاع الاتصال                                  |
| `atomic_schedule_compaction.sql`                           | جدول الإيصالات وإجراء التطبيق وإجراء قراءة النتيجة ومحفزات المدخلات                             |
| `compact-atomic-service.test.mjs`                          | اختبارات حقيقية للعميل مع استبدال حدود الاتصال فقط                                              |
| `compact-atomic-db.test.mjs` و`fixtures/atomic-compaction` | PostgreSQL 17 منفصل، بيانات TEST_ONLY، وإجراءات النقل وRBAC والمحفزات المأخوذة من المخطط الفعلي |
| `runtime-gates.yml`                                        | اختبارات العميل وبوابة PostgreSQL مستقلة ذات حاوية مؤقتة                                        |

اختبارات قاعدة البيانات لا تتصل بالإنتاج. يشترط المشغل عنوان localhost واسم قاعدة ينتهي بـ`_test` وتفويض اختبار صريح في متغير البيئة وقاعدة فارغة. تشمل الاختبارات نجاح النقل المترابط، فشل الخطوة الثانية، فشل التدقيق، تكرار الجلسة والطلب، الصلاحيات، الكلية الأجنبية، الأقفال، المدد والساعات، مراجعات المدخلات، إغلاقات القاعات، وحد الأيام والتزامن عبر اتصالات مستقلة. هوية JWT مصطنعة في قاعدة الاختبار؛ إجراءات الأدوار وإجراء النقل ومساعداته مأخوذة من المخطط المرصود. هذا اختبار تكامل للإجراء، وليس ادعاء إجراء UAT على بوابة الإنتاج.

أوامر البوابة:

```sh
node --test tests/compact.test.mjs tests/joint-attendance.test.mjs tests/v2-joint-orchestration.test.mjs tests/compact-worker-client.test.mjs tests/compact-atomic-service.test.mjs
node --test tests/compact-atomic-db.test.mjs
bunx tsc --noEmit
bun run build
bun run test:harness
```

الحكم الحالي: **HOLD للنشر الإنتاجي** حتى نجاح جميع البوابات على أحدث commit، وإدراج مصدر SQL في سير الترحيل المعتمد وتطبيقه والتحقق منه قبل نشر العميل. يُدوّن تقرير الإغلاق نتائج البوابات وروابط التشغيل الفعلية.

## المراجعة الأمنية وخطة التفعيل

- مصدر SQL جديد: نعم؛ ترحيل مسجل أو مطبق على الإنتاج في هذه المرحلة: لا.
- RLS: تفعيل على جدول الإيصالات الجديد فقط؛ لا إضعاف لسياسات الجداول الحالية.
- RPC: إجراءان جديدان، مع منح `EXECUTE` إلى `authenticated` فقط وفحص الصلاحية داخل الخادم. لا تغيير للمصادقة أو تعريف الأدوار.
- يستخدم الإجراء `SECURITY DEFINER` للمعاملة المصرح بها مع `search_path` فارغ وأسماء جداول مؤهلة؛ توصي [وثائق Supabase للإجراءات](https://supabase.com/docs/guides/database/functions) بضبط مسار البحث صراحة عند استخدام هذا النوع من الإجراءات.
- لا أسرار أو بيانات مدرّسين في ملفات الاختبارات. لا رسائل SQL خام أو بيانات كلية أخرى في نتيجة الخطأ.
- الأثر الحالي على الإنتاج: لا كتابة في هذه المرحلة. خطر التفعيل: متوسط، لوجود إجراء كتابة جديد وتوسيع مدخلات مراجعة النسخة.
- الجاهزية للدمج لا تعني الجاهزية للنشر. يجب تطبيق قاعدة البيانات قبل العميل؛ غياب الإجراء يوقف التطبيق ولا يعيده إلى النقل المتتابع.

قبل التفعيل: طابق هوية المشروع والمخطط والإجراءات الحالية مع المصدر المرصود؛ سجل أعداد الجلسات والإسنادات ومراجعات النسخ وRLS والصلاحيات. جهز ملف الترحيل عبر Supabase CLI وسجله في المستودع ثم طبقه بالمسار المعتمد. تعذر تشغيل CLI في بيئة العمل برسالة `network approval was cancelled before a decision was returned`، لذلك بقي التغيير مصدر SQL قابلًا للمراجعة بدل اختلاق ملف ترحيل أو تسجيل نجاحه.

بعد التطبيق: تحقق من وجود الجدول وإجراءي RPC ومحفزات المدخلات ومنع الأدوار غير المصرح بها؛ قارن أعداد بيانات الأعمال والصلاحيات القديمة بما قبل التطبيق، ثم اختبر طلبًا مصرحًا به ورفضًا واستكمالًا على نسخة TEST_ONLY معزولة قبل نشر العميل. بعد التطبيق وحده لا يُفترض أن تتغير أي جلسة؛ تبدأ التنقلات فقط بطلب تحسين مصرح به.

الرجوع عند عطل التفعيل: أوقف واجهة التطبيق الجديد وألغِ منح تنفيذ `apply_schedule_compaction` للمستخدمين. احتفظ بالإيصالات والتدقيق ومراجعات المدخلات؛ لا تحذف الجداول أو تعكس تلقائيًا خططًا نجحت بالفعل. لا تتطلب عودة واجهة سابقة حذف الإيصالات.

## حدود المرحلة والخطوة التالية

لا تضيف المرحلة بحثًا أكبر من خطوتين ولا تبادلًا متزامنًا يتطلب تجاوز تعارض مؤقت؛ يجب أن تكون كل خطوة مرتبة صالحة. لا تضمن انعدام الفراغات أو بلوغ الحل الأمثل. تبقى أهداف أربعة أيام وبحد خمسة، وثبات ساعات التدريس، وعدم إنشاء استراحات كما في الخطة الأساسية. يأتي توسيع البحث بعد إغلاق التفعيل الذري، مع بوابة قياس مستقلة لزمن البحث وتحسن الطرفين.
