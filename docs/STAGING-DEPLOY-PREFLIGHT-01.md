## مسار النشر المكتشف

- البناء يستخدم Nitro preset: `cloudflare-module`.
- ناتج البناء صالح تقنيًا لـWrangler.
- يولد Nitro إعداد Wrangler من الحزمة، ثم يستبدل workflow الاسم باسم
  `STAGING_WORKER_NAME` بعد اجتياز فحص العزل.
- يوجد workflow يدوي في `.github/workflows/deploy-staging.yml` ولا يستجيب لدفع تلقائي.
- لا توجد بيانات اعتماد Cloudflare أو Supabase staging في المصدر؛ مصدرها الوحيد GitHub
  Environment باسم `staging`.

التشغيل المباشر خارج workflow غير معتمد. يمنع الحارس التنفيذ إذا لم يختلف مشروع
Supabase التجريبي عن المشروع التشغيلي أو لم يحتو اسم Worker على `staging`.

- أي staging لقاعدة البيانات يجب أن يكون restore/clone مع ledger migrations مطابق، أو يخضع لخطة baseline مستقلة؛ لا يجوز تشغيل سلسلة migrations عمياء على قاعدة فارغة أو على الإنتاج.

## بوابة الانتقال التالية

يلزم قبل النشر التجريبي:

1. إنشاء GitHub Environment محمي باسم `staging` وإضافة القيم المحددة في
   `docs/STAGING-E2E-RUNBOOK-02.md`.
2. اعتماد مشروع Supabase تجريبي مستقل لا يحتوي بيانات حقيقية.
3. تشغيل workflow على SHA رأس الفرع نفسه ومراجعة أدلة PostgreSQL والمتصفح.
4. إبقاء أي اختبار كتابي لاحق داخل بيانات `TEST_ONLY` بخطة تنظيف دقيقة.

لا يصبح الإنتاج مسموحًا تلقائيًا بعد نجاح staging؛ يحتاج بوابة وتفويضًا منفصلين.
