# النسخ الاحتياطي والاستعادة — Supabase

هذا الإجراء يثبت قابلية استعادة **مخططات التطبيق** (`public` وجميع مخططات `*_private` التي تنشئها الترحيلات، مع سجل الترحيلات `supabase_migrations`) في قاعدة PostgreSQL معزولة، واختياريًا مخطط الهوية `auth`. لا يحل محل النسخ المدارة في Supabase أو الاستعادة الزمنية `PITR`، ولا يثبت أنهما مفعّلان.

## أهداف RPO / RTO

| المؤشر | الهدف | الآلية |
| --- | --- | --- |
| RPO (أقصى فقدان بيانات مقبول) | ≤ 24 ساعة بالنسخ اليومية المدارة؛ ≤ دقائق عند تفعيل PITR | Supabase Daily Backups / Point-in-Time Recovery |
| RTO (أقصى زمن استعادة مقبول) | ≤ 4 ساعات من قرار الاستعادة حتى عودة الخدمة | استعادة من لوحة Supabase + تحقق هذا الدليل |
| زمن الاستعادة المنطقية المقاس | يُسجَّل في ملف الدليل (`dump_s` / `restore_s` / `total_s`) | `scripts/local-db/backup-restore-drill.sh` |

إذا تجاوز الزمن المقاس في التمرين ربع هدف RTO، تُراجع الخطة (حجم القاعدة، الحاجة إلى PITR، أو ترقية الخطة).

## قواعد إلزامية

- لا تُنفذ الاستعادة فوق قاعدة الإنتاج أو أي قاعدة تحتوي بيانات حقيقية.
- قاعدة الوجهة يجب أن يكون اسمها بادئًا بـ `restore_drill_`، وأن تكون **فارغة**، وأن تحمل تسمية تشغيلية تبدأ بـ `disposable-`. الأداة لا تحذف شيئًا (لا تستخدم `pg_restore --clean`) وترفض وجهة فيها جداول.
- يجب اختلاف رابط المصدر عن رابط الوجهة.
- يمنع البرنامج استخدام مرجع مشروع الإنتاج في رابط الوجهة؛ يُقرأ المرجع من `supabase/config.toml` (`project_id`) ولا يُكتب داخل السكربت.
- لا تُحفظ روابط قواعد البيانات أو كلمات المرور أو ملفات التفريغ في Git أو artifacts عامة. ملف الدليل يحتوي فقط التسمية والأعداد والأزمنة.
- تشغيل الأداة يحتاج الإقرار الصريح `RESTORE_DRILL_ACK=DISPOSABLE_ONLY`.

## Preflight — قراءة فقط

1. افتح لوحة Supabase الرسمية (Database → Backups) وتحقق من تاريخ آخر نسخة ناجحة، مدة الاحتفاظ، وحالة PITR.
2. سجّل نقطة الاستعادة المستهدفة وRPO/RTO المتوقعين دون تغيير الإعدادات.
3. أنشئ قاعدة PostgreSQL مؤقتة مستقلة (نفس الإصدار الرئيسي للإنتاج) باسم يبدأ بـ `restore_drill_`، ولا تربطها بتطبيق الإنتاج.
4. جهّز رابط مصدر بصلاحية قراءة مناسبة ورابط وجهة مؤقتة بصلاحية الاستعادة.
5. إن كان المصدر مشروع Supabase، فأنشئ في الوجهة الأدوار `anon` و`authenticated` و`service_role` ومخطط `auth` بجدول `auth.users` أدنى (أو استخدم `INCLUDE_AUTH=1`)، لأن سياسات RLS والمفاتيح الأجنبية تشير إليها.

إذا تعذر إثبات النسخة أو PITR، فالقرار `HOLD` حتى لو نجح الاختبار المنطقي المحلي.

## تشغيل الاختبار المعزول

```bash
RESTORE_DRILL_ACK=DISPOSABLE_ONLY \
RESTORE_TARGET_LABEL=disposable-quarterly-drill \
SOURCE_DATABASE_URL='postgresql://…' \
RESTORE_DATABASE_URL='postgresql://…/restore_drill_2026q4' \
bash scripts/local-db/backup-restore-drill.sh
```

خيارات:

- `INCLUDE_AUTH=1` — يضيف مخطط `auth` (المستخدمون والهويات والجلسات). انظر القيود أدناه.
- `EVIDENCE_DIR=<dir>` — مكان ملف الدليل (الافتراضي `docs/operations/drills/`).
- `DRILL_NO_EVIDENCE=1` — بدون ملف دليل (للتجارب).

تقوم الأداة بما يلي:

1. تحديد مخططات التطبيق تلقائيًا (كل ما عدا مخططات منصة Supabase: `auth`, `storage`, `extensions`, `realtime`, `vault`, …).
2. إعادة إنشاء الامتدادات بنفس مخططاتها في الوجهة أولًا (`btree_gist` في `public`، و`pgcrypto`/`uuid-ossp`/`pg_trgm` في `extensions`) — التفريغ المقيّد بمخطط لا يحمل `CREATE EXTENSION`، وبدونها تفشل قيود الاستبعاد `EXCLUDE USING gist` (اكتُشف ذلك في أول تشغيل محلي للتمرين).
3. تفريغ واحد بصيغة custom لكل المخططات معًا (لحفظ ترتيب الاعتماديات بينها)، ثم الاستعادة مع `--exit-on-error`.
4. مقارنة **عدد الصفوف لكل جدول** في المصدر والوجهة (وليس عدد الجداول فقط). أي اختلاف يفشل التمرين ويعرض اسم الجدول فقط.
5. طباعة سطر `RESTORE_DRILL_PASS …` وكتابة ملف دليل `docs/operations/drills/restore-drill-<UTC>.txt` (التسمية، المخططات، عدد الجداول والصفوف، الأزمنة، commit، والأعداد لكل جدول — بلا أسرار).

### مخطط auth — القيود

- مخطط `auth` مملوك لـ `supabase_auth_admin` على المنصة. استعادته في مشروع Supabase آخر عبر `pg_restore` **غير مدعومة** (الجداول موجودة مسبقًا ومملوكة لدور آخر). استخدم `INCLUDE_AUTH=1` فقط مع وجهة PostgreSQL عادية فارغة للتحقق من اكتمال البيانات.
- مسار الاستعادة الحقيقي للمستخدمين هو استعادة المشروع كاملًا من لوحة Supabase (Backups أو PITR)، أو `Restore to new project`، وهي تستعيد `auth` و`storage` مع التطبيق.
- ملفات Storage (الكائنات نفسها) ليست في قاعدة البيانات؛ لا يغطيها هذا التمرين.
- جدول `auth.users` يحتوي تجزئات كلمات المرور: ملف التفريغ سري ويُحذف تلقائيًا من المجلد المؤقت عند انتهاء الأداة.

## Post-verify

- تحقق من ظهور `RESTORE_DRILL_PASS` وعدم وجود أخطاء قبله، ومن أن ملف الدليل أُنشئ.
- نفّذ على الوجهة المؤقتة اختبارات SQL الذاتية (انظر `README.md` → اختبارات SQL) أو على الأقل:
  ```sql
  select count(*) from public.colleges;
  select count(*) from public.schedule_versions where status = 'published';
  select max(version) from supabase_migrations.schema_migrations;
  ```
- سجّل `total_s` مقابل هدف RTO.
- احذف قاعدة الاختبار المؤقتة من خلال إجراء منفصل ومعرّف دقيق بعد حفظ دليل النجاح؛ لا تضف حذفًا تلقائيًا إلى هذا البرنامج.
- أضف ملف الدليل إلى Git في commit مستقل (`docs/operations/drills/`).

## قائمة الفحص الربع سنوية

| # | البند | المسؤول | الدليل |
| --- | --- | --- | --- |
| 1 | آخر نسخة يومية ناجحة عمرها < 24 ساعة | مسؤول المنصة | لقطة من Backups |
| 2 | حالة PITR ومدة الاحتفاظ مطابقة للخطة | مسؤول المنصة | لقطة من Backups |
| 3 | تشغيل `backup-restore-drill.sh` على وجهة `restore_drill_<YYYYqN>` | مسؤول قاعدة البيانات | `docs/operations/drills/restore-drill-*.txt` |
| 4 | تمرين `INCLUDE_AUTH=1` على PostgreSQL عادية | مسؤول قاعدة البيانات | ملف دليل ثانٍ |
| 5 | (سنويًا) `Restore to new project` من لوحة Supabase وتشغيل التطبيق عليه بقراءة فقط | مسؤول المنصة + ضمان الجودة | محضر مختصر |
| 6 | مقارنة `total_s` بهدف RTO وتحديث الجدول أعلاه إن لزم | قائد الفريق | هذا الملف |
| 7 | فحص انحراف الترحيلات (`migration-drift` workflow) أخضر | مسؤول الإصدار | رابط التشغيل |
| 8 | حذف قواعد التمرين المؤقتة وتوثيق ذلك | مسؤول قاعدة البيانات | محضر |

## بوابة القرار

- `PASS`: نسخة مدارة حديثة مثبتة، PITR مثبت حسب الخطة، واختبار الاستعادة المعزول ناجح مع ملف دليل.
- `PASS_WITH_NOTES`: الاختبار المنطقي ناجح، لكن PITR غير مطلوب أو غير مشمول بالخطة مع توثيق ذلك.
- `HOLD`: حالة النسخ/PITR غير مثبتة، أو لا توجد وجهة مؤقتة آمنة.
- `BLOCKED`: لا يوجد وصول رسمي إلى لوحة Supabase أو بيانات اتصال اختبارية.
